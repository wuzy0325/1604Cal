## 1. 现状总览

### 1.1 当前工程定位

当前工程（Cal1604）是一个基于 **Wails v2 (Go + Vue 3)** 的桌面标定系统，用于对 WTN1604/1605 系列压力扫描阀进行多点压力校准。核心流程：连接设备 → 通道选择 → 逐点打压/采集 → 数据拟合 → 报告导出。

### 1.2 技术栈现状

| 层次 | 当前工程 | 标定参考文档(1605计量) | 计量参考文档(1604标定) |
|------|----------|----------------------|----------------------|
| 桌面框架 | **Wails v2 (Go)** | Electron (Node.js) | Electron (Node.js) |
| 后端语言 | **Go** | TypeScript (主进程) | TypeScript (主进程) |
| 前端框架 | Vue 3 + Pinia | Vue 3 + Pinia | Vue 3 + Pinia |
| 通信机制 | **REST API + SSE** | IPC (ipcMain/ipcRenderer) | IPC (ipcMain/ipcRenderer) |
| UI组件库 | Element Plus | Element Plus | Element Plus |
| 构建工具 | Vite + Wails | Vite + Electron Builder | electron-vite + Vite |
| 设备通信 | Go TCP驱动 | TypeScript SCPI/TCP | TypeScript SCPI/TCP |
| 报告导出 | Go Excel模板 | TypeScript xlsx | CSV |

**关键差异**：当前工程已从 Electron + TypeScript 架构迁移至 Wails + Go 架构，通信机制从 IPC 变为 REST API + SSE。

### 1.3 架构成熟度评估

| 维度 | 当前状态 | 参考目标 | 差距等级 |
|------|----------|----------|----------|

| 状态管理 | 会话状态机(基本) | 完整状态机+采集状态机 | 中 |

| 事件系统 | 进程内事件总线+SSE | IPC事件推送 | 低(已适配) |
| 数据持久化 | JSON文件(原子写入) | JSON文件+配置服务 | 低 |
| 前端复用 | 无Composables | Composables层 | 中 |

| Mock/模拟 | 无独立模拟层 | BaseSimulator+浏览器预览 | 高 |

### 3.2 校准流程现状

当前校准流程由 `calibration/service.go` 编排，核心流程：

```
1. 验证配置 (通道非空, 压力点2-6个, 采样次数1-100)
2. 检查设备连接 (1604必须, 打压可选)
3. 开始校准 → 1604设备 startCalibration
4. 阀门切换到校准状态 (必须成功)
5. 逐点采集:
   a. 打压 → setTargetPressure (自动模式)
   b. 等待稳定 → waitForStability (轮询)
   c. 采集数据 → Collect (多次平均)
   d. 报警检查 → alarmService
   e. 完成当前点
6. 执行拟合 → 1604设备 performFitting
7. 结束校准 → 1604设备 endCalibration
8. 阀门切换回测量状态 (容错)
```

## 4. 与参考架构的差距分析

### 4.1 严重差距

#### (1) 缺少断路器 (CircuitBreaker)

**现状**：仅有简单的重试+退避逻辑（`retryWithBackoff`），无熔断保护。

**风险**：设备持续故障时，每次请求都执行完整重试，可能导致：
- 系统资源浪费（频繁TCP连接尝试）
- 用户体验差（长时间等待超时）
- 级联故障（多设备场景下一个故障设备拖慢整体流程）

**参考实现**：标定文档描述了完整的断路器状态机（CLOSED → OPEN → HALF_OPEN），连续失败达阈值后熔断，超时后试探恢复。

#### (2) 缺少独立模拟层 (Mock/Simulator)

**现状**：无独立的设备模拟器，开发和测试依赖真实硬件。

**风险**：
- 无法在没有硬件的环境下开发和调试
- 前端无法独立运行和测试
- CI/CD 流水线无法自动化测试
- 新开发者上手困难

**参考实现**：标定文档有 BaseSimulator（可配置延迟、错误概率），计量文档有浏览器预览模式（模拟API注入）。

#### (3) 缺少前端 Composables 层

**现状**：业务逻辑直接写在 Store 或组件中，无 Composables 复用层。

**风险**：
- 采集命令逻辑与 Store 状态管理耦合
- 事件监听逻辑分散在多个组件中
- 报警配置逻辑无法复用
- 组件代码膨胀

**参考实现**：标定文档定义了 useCollectionCommands、useCollectionEvents、useAlarmConfig 三个核心 Composable。

### 4.2 中等差距

#### (4) 设备驱动单文件实现

**现状**：5个设备驱动全部在 `tcp_connection_driver.go` 单文件中。

**风险**：
- 文件过大，难以维护
- 新增设备型号需修改同一文件
- 不同驱动的测试无法独立进行
- 缺少策略模式，SCPI命令差异硬编码在各驱动中

**参考实现**：标定文档使用 ScpiStrategy 策略模式，每种设备型号有独立的命令策略；计量文档使用 AbstractPressDevice 模板方法+钩子方法模式。

#### (5) 缺少独立的 RetryStrategy 组件

**现状**：重试逻辑内联在 deviceconnect/service.go 中，参数固定。

**风险**：
- 不同设备/操作无法配置不同的重试策略
- 无法区分可重试错误和不可重试错误
- 校准流程中的数据采集超时无独立重试配置

**参考实现**：标定文档的 RetryStrategy 支持可配置参数（maxRetries, baseDelay, maxDelay, backoffMultiplier, retryableErrors）。

#### (6) 报警机制不完整

**现状**：存在 alarm_service.go，但缺少：
- 声音报警
- 用户确认交互（继续/重试选择）
- 报警事件推送到前端
- 通道级报警启用/禁用

**参考实现**：标定文档的报警机制包含完整的声音提示、用户确认Promise等待、通道级控制。

#### (7) 报告导出功能不完整

**现状**：仅有模板路径选择，缺少：
- 实际Excel文件生成
- 导出进度回调
- 前端输出路径选择（原生文件对话框）

**参考实现**：标定文档的 ReportService 完整实现了Excel生成、进度回调、原生对话框。

#### (8) 前后端类型不同步

**现状**：前端 TypeScript 接口在 apiClient.ts 中手动维护，与后端 Go 结构体手动对齐。

**风险**：
- 接口变更时容易遗漏同步
- 运行时才发现类型不匹配
- 无编译期保障

### 4.3 轻微差距

#### (9) 缺少共享类型/常量目录

**现状**：无 shared 目录，前后端各自定义类型。

**参考实现**：标定文档有 shared/types + shared/constants 跨进程共享。

#### (10) 配置服务不独立

**现状**：配置通过 AppConfig 结构体 + JSON 文件加载，无独立的配置服务。

**参考实现**：标定文档的 ConfigService 管理多种配置（校准参数、报警配置、设备选择），支持部分更新和重置默认。

#### (11) 缺少输入验证器

**现状**：验证逻辑分散在各 Handler 和 Service 中。

**参考实现**：计量文档有独立的 validators.ts（validateIP, validatePressure, validateChannels 等）。

#### (12) 日志工具不完善

**现状**：Go 端使用标准 log 包，无结构化日志。

**参考实现**：计量文档有中英文双语日志工具，自动检测编码环境。

## 5. 改善建议

### 5.1 [P0] 引入断路器模式

**目标**：防止设备故障时系统资源耗尽和级联失败。

**实施方案**：

```
internal/resilience/
├── circuit_breaker.go    # 断路器实现
├── retry_strategy.go     # 独立重试策略
└── config.go             # 弹性配置
```

断路器状态机：
```
CLOSED (正常) ──连续失败达阈值──> OPEN (熔断)
OPEN ──超时后──> HALF_OPEN (试探)
HALF_OPEN ──试探成功──> CLOSED
HALF_OPEN ──试探失败──> OPEN
```

关键配置：
- `failureThreshold`: 触发熔断的连续失败次数（默认5）
- `resetTimeout`: 熔断超时时间（默认30s）
- `halfOpenMaxAttempts`: 半开状态最大试探次数（默认1）

集成点：在 `deviceconnect/service.go` 中包装设备操作，每个设备实例维护独立的断路器。

### 5.2 [P0] 建立设备模拟层

**目标**：支持无硬件开发调试、前端独立运行、自动化测试。

**实施方案**：

```
internal/infrastructure/driver/
├── mock/
│   ├── mock_pressure_driver.go   # 打压设备模拟
│   ├── mock_measure_driver.go    # 计量设备模拟
│   └── config.go                 # 模拟配置(延迟/错误率)
```

模拟行为：
- 连接：可配置延迟（默认500ms）
- 打压：可配置延迟 + 压力值模拟（目标值 ± 随机波动）
- 采集：生成模拟通道数据（基准值 + 通道偏移 + 随机噪声）
- 稳定度：可配置稳定延迟
- 错误注入：可配置错误概率，模拟设备异常

前端独立模式：在 apiClient.ts 中检测后端不可用时，自动切换到前端模拟API（参考计量文档的浏览器预览模式）。

配置方式：
- 环境变量 `CAL1604_MOCK=true` 启用模拟
- AppConfig 中 `UseMock` 字段
- 驱动工厂根据配置返回模拟驱动或真实驱动

### 5.3 [P0] 建立前端 Composables 层

**目标**：解耦业务逻辑与状态管理，提高代码复用性。

**实施方案**：

```
web/src/composables/
├── useCollectionCommands.ts   # 采集命令封装
├── useCollectionEvents.ts     # 采集事件监听
├── useAlarmConfig.ts          # 报警配置管理
├── useDeviceConnection.ts     # 设备连接通用逻辑
└── usePressureMonitor.ts      # 压力实时监控
```

**useCollectionCommands**：
- 封装校准流程的 API 调用序列（init → setControlMode → start）
- 提供类型安全的操作接口
- 统一错误处理和状态回滚

**useCollectionEvents**：
- 封装 SSE 事件监听逻辑
- 自动映射事件到 Store 状态更新
- 提供 cleanup 清理函数
- 替代各组件中分散的事件监听代码

**useAlarmConfig**：
- 封装报警配置的加载、持久化和自动保存
- 防抖保存（250ms）
- 监听配置变更自动同步

### 5.4 [P1] 拆分设备驱动为独立文件

**目标**：提高可维护性，支持独立测试，为策略模式做准备。

**实施方案**：

```
internal/infrastructure/driver/
├── factory.go                    # 驱动工厂(保留)
├── tcp_connection_driver.go      # TCP连接基础能力(保留，提取公共部分)
├── scpi/
│   ├── scpi_base.go              # SCPI基础命令集
│   ├── const811a.go              # ConST 811A 驱动
│   ├── const820.go               # ConST 820 驱动
│   ├── const860.go               # ConST 860 驱动
│   └── spc4000.go                # SPC4000 驱动
├── wtn1604/
│   └── wtn1604_driver.go         # WTN1604 驱动
└── mock/
    ├── mock_pressure_driver.go
    └── mock_measure_driver.go
```

进一步可引入 SCPI 策略模式：
```go
type ScpiStrategy interface {
    InitSequence() []string           // 连接后初始化命令
    ApplyPressure(value float64) []string  // 打压命令序列
    ParsePressure(resp string) (float64, error)
    // ...
}
```

### 5.5 [P1] 独立重试策略组件

**目标**：为不同设备/操作提供可配置的重试机制。

**实施方案**：

```go
type RetryConfig struct {
    MaxRetries       int           // 最大重试次数
    InitialBackoff   time.Duration // 初始退避时间
    MaxBackoff       time.Duration // 最大退避时间
    BackoffMultiplier float64      // 退避倍数
    RetryableErrors  []string      // 可重试的错误码
}

func RetryWithConfig(ctx context.Context, cfg RetryConfig, op func() error) error
```

不同场景的推荐配置：
| 场景 | MaxRetries | InitialBackoff | MaxBackoff |
|------|-----------|---------------|------------|
| 设备连接 | 3 | 80ms | 300ms |
| 设备断开 | 2 | 40ms | 120ms |
| 数据采集 | 2 | 500ms | 2000ms |
| SCPI命令 | 3 | 200ms | 1000ms |

### 5.6 [P1] 完善报警机制

**目标**：实现完整的报警交互流程。

**改善项**：
1. **声音报警**：通过前端 Web Audio API 或系统通知实现提示音
2. **用户确认**：报警事件通过 SSE 推送到前端，前端弹出确认对话框（继续/重试），用户选择后通过 REST API 回传
3. **通道级控制**：AlarmConfig 增加 EnabledChannels 字段，仅对启用通道执行报警检查
4. **报警事件流**：
   ```
   Go端检测超限 → events.Bus发布报警事件
   → SSE推送到前端 → 前端弹出确认对话框
   → 用户选择 → REST API回传 → Go端继续/重试
   ```

### 5.7 [P1] 完善报告导出

**目标**：实现完整的Excel报告生成和导出流程。

**改善项**：
1. **Excel生成**：使用 Go 的 excelize 库根据模板填充数据生成 Excel 文件
2. **导出进度**：通过 SSE 推送导出进度百分比
3. **路径选择**：Wails Runtime 的 OpenFileDialog 选择输出路径
4. **数据完整性验证**：导出前验证采集会话数据完整性

### 5.8 [P2] 前后端类型同步

**目标**：消除前后端类型手动对齐的风险。

**可选方案**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| OpenAPI/Swagger 生成 | 自动化、标准化 | 需要维护API文档 |
| Go 结构体 → JSON Schema → TS 类型 | 端到端自动 | 工具链复杂 |
| 共享 JSON Schema 定义 | 单一数据源 | 需要额外构建步骤 |
| 手动对齐 + CI 校验 | 简单、可控 | 仍有遗漏风险 |

**推荐**：短期采用"手动对齐 + CI校验"（添加API契约测试），中期考虑引入 OpenAPI 规范。

### 5.9 [P2] 独立配置服务

**目标**：统一管理多种配置，支持部分更新和运行时修改。

```go
type ConfigService struct {
    store    DeviceStore       // 设备配置存储
    calibCfg CalibrationConfig // 校准参数
    alarmCfg AlarmConfig       // 报警配置
    appCfg   AppConfig         // 应用配置
}

func (s *ConfigService) SaveCalibrationConfig(partial CalibrationConfig) error
func (s *ConfigService) SaveAlarmConfig(partial AlarmConfig) error
func (s *ConfigService) ResetToDefaults() error
```

### 5.10 [P2] 输入验证器独立化

**目标**：集中验证逻辑，提高复用性和一致性。

```go
internal/validation/
├── device.go    # ValidateIP, ValidatePort, ValidateDeviceType
├── calibration.go  # ValidateChannels, ValidatePressurePoints, ValidateAverageCount
└── pressure.go  # ValidatePressure, ValidatePressureRange
```

前后端双重验证：Go 端验证器作为最终防线，前端 TypeScript 验证器提供即时反馈。

### 5.11 [P2] 结构化日志

**目标**：替换标准 log 包，支持结构化日志、日志级别、文件输出。

推荐使用 `zerolog` 或 `slog`（Go 1.21+），支持：
- JSON 格式结构化输出
- 日志级别控制（DEBUG/INFO/WARN/ERROR）
- 设备操作审计日志
- 前端日志通过 API 转发到后端统一记录

### 5.12 [P3] 前端 Store 整合

**目标**：解决 deviceStore 与 measurement/deviceStore 职责重叠问题。

方案：
- 保留顶层 `deviceStore` 作为设备管理的唯一入口
- `measurement/deviceStore` 改为从顶层 store 派生的 Composable 或子模块
- 明确各 Store 的职责边界，避免状态分散

## 6. 改善优先级与路线图

### 优先级定义

| 等级 | 含义 | 标准 |
|------|------|------|
| P0 | 必须尽快实施 | 影响系统可靠性和开发效率的关键缺陷 |
| P1 | 应当近期实施 | 影响功能完整性和用户体验的重要差距 |
| P2 | 建议中期实施 | 提升代码质量和可维护性的改善 |
| P3 | 可长期规划 | 锦上添花的优化项 |

### 实施路线图

```
阶段1: 可靠性基建 (P0)
├── 引入断路器模式
├── 建立设备模拟层
└── 建立前端 Composables 层

阶段2: 功能补全 (P1)
├── 拆分设备驱动为独立文件
├── 独立重试策略组件
├── 完善报警机制
└── 完善报告导出

阶段3: 质量提升 (P2)
├── 前后端类型同步
├── 独立配置服务
├── 输入验证器独立化
└── 结构化日志

阶段4: 优化打磨 (P3)
└── 前端 Store 整合
```

### 各阶段预期收益

| 阶段 | 收益 |
|------|------|
| 阶段1 | 设备故障不再拖垮系统；无硬件可开发调试；前端代码复用度提升 |
| 阶段2 | 设备驱动可独立维护和测试；报警交互完整；报告导出可用 |
| 阶段3 | 前后端接口变更自动检测；配置管理统一；验证逻辑集中；日志可追溯 |
| 阶段4 | 前端状态管理清晰无冗余 |
