## 一、概述

本报告对比分析了参考项目（1605MeassureApp，Electron + Vue3 + TypeScript）和当前项目（Cal1604，Go + Wails + Vue3）的计量模块实现，识别出业务逻辑错误和未完成的功能。

---

## 二、业务逻辑错误

### 2.1 【严重】计量采集服务状态机过于简化

**问题描述:**

当前项目的计量采集服务 (`internal/application/measurement/service.go`) 仅实现了 3 态状态机：
```
idle -> collecting -> paused
```

而参考项目实现了完整的采集生命周期管理，包括：
- `idle` - 空闲
- `pressuring` - 打压中
- `stabilizing` - 稳定中
- `collecting` - 采集中
- `paused` - 已暂停
- `completed` - 已完成
- `error` - 错误

**影响:**
- 无法准确反映采集流程的当前阶段
- 前端无法根据状态显示正确的 UI（如打压进度、稳定等待）
- 错误处理不完善

**建议修复:**
扩展状态机，增加 `pressuring`、`stabilizing`、`completed`、`error` 状态。

---

### 2.2 【严重】校准服务缺少完整的自动采集流程

**问题描述:**

当前项目的校准服务 (`internal/application/calibration/service.go`) 虽然有 `RunAutoCollection` 方法，但缺少以下关键流程控制：

1. **缺少压力点状态跟踪**
   - 参考项目: 每个压力点有独立状态 (`pending`, `pressuring`, `stabilizing`, `collecting`, `completed`, `error`)
   - 当前项目: 仅在内存中记录，无持久化状态

2. **缺少采集会话管理**
   - 参考项目: `CollectionSession` 包含完整的会话信息（开始时间、结束时间、配置、压力点数据）
   - 当前项目: 会话数据结构不完整

3. **缺少暂停/恢复的精确控制**
   - 参考项目: 暂停后可精确恢复到当前压力点继续采集
   - 当前项目: 暂停/恢复逻辑不完善

**影响:**
- 采集过程中断后无法正确恢复
- 无法追踪每个压力点的采集状态
- 前端无法显示详细的采集进度

---

### 2.3 【中等】报警处理逻辑不完整

**问题描述:**

参考项目的报警处理包含完整的决策流程：
```typescript
type AlarmResolutionAction = 
  | 'continue'      // 继续采集
  | 'skip'          // 跳过当前点
  | 'recollect'     // 重新采集
  | 'stop'          // 停止采集
```

当前项目 (`internal/workflow/alarm_service.go`) 仅实现了报警判定，缺少：
- 报警决策的执行逻辑
- `skip` 跳过当前点的处理
- `recollect` 重新采集的处理
- 报警历史记录

**影响:**
- 报警触发后用户无法选择处理方式
- 无法跳过问题压力点继续采集

## 七、总结

当前项目的计量模块在核心架构上已经搭建完成，但在业务逻辑完整性和功能实现上与参考项目存在较大差距。主要问题集中在：

1. **状态管理不完善** - 状态机过于简化，无法准确反映采集流程
2. **流程控制不完整** - 自动采集流程缺少精确的暂停/恢复控制
3. **设备功能缺失** - 阀门控制、调零校准等关键功能未实现
4. **用户体验不足** - 缺少实时进度显示、报警处理等交互功能

建议按照优先级逐步完善，首先解决 P0 级别的核心问题，确保基本采集流程的正确性。
